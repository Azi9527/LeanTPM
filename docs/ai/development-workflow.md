# 通用 AI 开发流程

## 1. 目的与适用范围

本流程用于开发、修复、重构、审查和清理任务。它以可复现的需求、风险驱动的验证、最小变更和可回滚交付为核心。任何项目特定信息必须在单次任务记录中填写，不得写入本通用规范。

强制原则：

- 用户未提交内容始终属于用户；不覆盖、不清理、不暂存、不自动 stash。
- 不以降低风险等级的方式减少测试。
- 未授权不得写数据库、部署、调用产生外部副作用的服务、提交、推送或创建 PR。
- 证据优先于推断；每个“通过”都要能指向命令、报告或截图。
- 只启用与任务范围有关的专项门禁和角色。

配套文件：

- [任务模板](task-template.md)
- [Feature flag 登记表](feature-flags.md)
- [AI 报告目录说明](../../reports/ai/README.md)

## 2. 当前仓库已确认的命令

以下命令来自仓库配置或脚本。进入相应子项目后执行，除非命令明确要求在仓库根目录运行。

| 目的 | 已确认命令 | 条件 |
|---|---|---|
| 服务端单元测试 | `mvn test` | 涉及服务端时 |
| 数据库集成测试 | `.\scripts\run-mysql-integration.ps1 -MySqlUser <user> -MySqlPassword '<secret>'` | 涉及持久化且获准创建临时测试库时；禁止把密码写入报告 |
| Web 类型检查 | `npm run typecheck` | 涉及 Web 客户端时 |
| Web 生产构建 | `npm run build` | 涉及 Web 客户端时 |
| 跨端客户端检查与测试 | `npm run verify` | 涉及跨端客户端时 |
| 跨端客户端平台构建 | `npm run build:h5`、`npm run build:weixin`、`npm run build:app` | 仅验证目标平台时 |
| 发布验证聚合脚本 | `.\scripts\verify-release.ps1 -MySqlUser <user> -MySqlPassword '<secret>'` | 发布候选且获准执行数据库集成验证时 |
| Android 调试构建 | `.\scripts\build-android.ps1 -Configuration Debug` | 涉及 Android 且环境齐备时 |
| Git 空白错误检查 | `git diff --check` | 所有代码或文档变更 |

尚未从仓库确认以下统一命令；在命令被正式加入仓库前不得猜测执行：

- `[待确认：Web 浏览器 E2E 命令]`
- `[待确认：统一 lint 命令]`
- `[待确认：统一格式检查命令]`
- `[待确认：独立 API 合同测试命令]`

缺少命令不等于可以跳过验证。应记录缺口，并采用经授权、可复现的最窄替代验证。

## 3. 端到端开发闭环

### 3.1 需求输入

使用[任务模板](task-template.md)记录目标、可信基线、允许修改范围、非目标、授权和环境。口头补充必须合并回任务记录，避免只存在于对话上下文。

### 3.2 需求理解完整性检查

编码前填写：

| 类型 | 当前理解 |
|---|---|
| 真实问题 | |
| 明确需求 | |
| 涉及对象 | |
| 涉及模块 | |
| 可能歧义 | |
| 必须确认 | |
| 默认假设 | |
| 假设影响 | |

满足以下任一条件时必须暂停并确认：不同理解会改变数据、权限、外部副作用、兼容性或交付范围；缺失信息无法通过只读调查获得；默认假设可能造成不可逆结果。

### 3.3 Given / When / Then 验收标准

每条需求至少包含一组可执行验收标准：

```text
Given [明确的前置数据、身份、配置与系统状态]
When  [唯一且可观察的操作]
Then  [业务结果、数据结果、错误或副作用]
And   [刷新、重试、重新登录或其他持久性要求]
```

验收清单必须按任务适用范围覆盖：

- 正常场景；
- 异常场景；
- 边界场景；
- 空数据；
- 权限不足；
- 外部依赖失败；
- 持久化失败；
- 刷新和重新登录；
- 并发或重复提交；
- 数据一致性；
- 旧逻辑兼容；
- 不影响其他模块。

不适用的项目应写明“不适用及原因”，而不是静默省略。

### 3.4 环境和工作区预检

首先执行只读命令：

```powershell
git status --short --branch
git worktree list --porcelain
git rev-parse HEAD
```

记录当前分支、提交、工作树、用户未提交文件和运行环境。禁止自动 reset、clean、stash、切换分支、覆盖文件或格式化无关文件。发现与任务文件重叠的用户变更时，先比较并说明合并方案；无法安全合并则暂停。

### 3.5 代码影响分析

先识别入口、核心符号、调用方、数据模型、共享合同、消费者、测试和部署路径。

GitNexus 可用时：

1. 执行 `gitnexus status`。
2. 索引缺失或 stale 时执行普通 `gitnexus analyze`，不默认使用 `--force`。
3. 陌生代码先用 `query` 定位流程。
4. 修改符号前使用 `context` 和上游 `impact`。
5. HIGH 或 CRITICAL 先告警、缩小范围并强化回滚与测试。
6. 提交前运行 `detect-changes`，并与预期影响清单比对。

CLI 或工具暂时不可用时，应记录原因和替代的只读调用链调查，不得声称已执行影响分析工具。

输出影响清单：直接修改、间接消费者、共享数据、兼容性、迁移、缓存、权限、UI、API、作业、外部依赖和回滚触点。

### 3.6 风险分级

| 等级 | 定义 | 最低治理要求 |
|---|---|---|
| L0 | 文档、注释、非运行时格式 | 主代理检查；链接与格式验证 |
| L1 | 局部、低影响、无合同变化的小修改 | 相关测试；局部审查；最窄回归 |
| L2 | 单模块行为、Service、Controller、API 或状态计算 | 多角色治理；失败测试；模块回归；测试与审查角色 |
| L3 | 持久化、缓存、删除、状态转换、共享数据展示或核心业务计算 | 架构审查；数据库/API/UI条件化验证；真实业务流；回滚演练或证据 |
| L4 | 数据库结构、权限、路由、共享组件、核心实体、跨模块合同和关键业务主链 | 先告警；最小化变更；完整角色矩阵；兼容迁移；Feature flag 或等效回滚；全链路回归 |

风险取所有影响中的最高等级。为减少测试而降低等级属于流程违规。

### 3.7 测试矩阵

编码前列出：

| 场景 | 层级 | 数据/身份 | 预期结果 | 命令或工具 | 证据路径 |
|---|---|---|---|---|---|
| 正常 | 单元/组件/集成/E2E | | | | |
| 异常 | | | | | |
| 边界 | | | | | |
| 兼容 | | | | | |
| 回滚 | | | | | |

测试应同时覆盖输入、输出、持久化、副作用和重新读取结果。对于状态型缺陷，至少覆盖创建、更新、停用/删除、恢复或重复执行的完整链路。

### 3.8 多角色与文件所有权

L2 以上任务必须启用多角色治理；角色可由独立代理承担，也可在不支持并行代理时以明确的独立审查阶段承担，但实现者不得替代最终独立审查结论。

通用角色：

- 主代理：统筹、影响分析、所有权、集成、最终验证和交付。
- 产品经理：需求、歧义、验收和范围。
- 架构师：模块边界、合同、数据流、回滚和回归范围。
- 领域/算法工程师：仅在复杂领域逻辑、算法或性能任务中启用。
- 前端工程师：仅在页面、状态或交互任务中启用。
- 后端工程师：仅在服务、API 或持久化任务中启用。
- 测试工程师：L2 以上独立验证，默认只读。
- 代码审查工程师：L2 以上独立审查，默认只读。

编码前必须输出：

| 角色 | 任务 | 文件/模块所有权 | 是否只读 | 是否允许修改测试 |
|---|---|---|---|---|
| | | | | |

不得为了展示而启用无关角色。每个实现角色必须有不重叠或显式协调的所有权；不得覆盖用户或其他角色修改。长日志写入 `reports/ai/`。测试修复最多三轮，审查修复最多三轮。

### 3.9 基线验证

在改动前运行与范围相符的最窄现有测试并记录结果。若基线已经失败，区分“既有失败”和“本任务新增失败”；不得把既有失败伪装成本次通过，也不得无授权扩大范围修复。

### 3.10 技术方案

方案至少说明：变更点、数据流、合同、异常处理、权限、幂等/并发、兼容性、测试、监控和回滚。优先局部修复，避免顺手重构和跨范围清理。

### 3.11 Feature flag 和回滚设计

L3/L4 新行为优先使用 Feature flag、配置切换或可快速恢复的旧路径。必须定义：默认值、ON/OFF 行为、数据兼容、监控、操作者、退休条件和回滚步骤，并登记到[Feature flag 登记表](feature-flags.md)。

若没有现成机制，不得临时发明未经评审的框架；应设计最小可撤销方案并将实现作为显式范围。临时验证开关通过后删除；保留开关必须有退休条件。

### 3.12 失败测试

实现前先写能稳定复现问题或表达新行为的失败测试。测试必须因目标行为缺失而失败，而不是因环境、语法或无关错误失败。不能先写测试时，记录具体原因、替代验证和补测时间点。

### 3.13 最小实现

只修改实现验收标准所必需的代码。遵守已有模式、组件和合同；避免大范围格式化、重命名、依赖升级或无关清理。

### 3.14 最窄测试

先运行刚新增或最直接相关的测试。失败时保存错误摘要，先定位根因再修改；同一失败命令最多重试三次。

### 3.15 模块回归

最窄测试通过后运行所属模块测试，并验证相邻状态、旧逻辑和共享消费者。L2 以上不得仅凭单个单元测试交付。

### 3.16 UI / API / 数据库条件化验证

仅当任务实际涉及对应范围时启用。

#### UI

- 阅读现有设计系统、主题和组件规范；优先复用批准组件。
- 执行组件测试、类型检查和生产构建。
- 用真实浏览器验证加载、交互、空态、错误态、权限态、刷新和响应式布局。
- 保存关键截图、控制台摘要和可用 trace；不得仅以代码阅读代替浏览器验证。

#### API

- 验证客户端和服务端的路径、方法、请求、响应、空值、错误码、权限和版本合同一致。
- 增加合同测试；检查重复请求、超时、依赖失败和向后兼容。
- 对写操作验证实际持久化结果，不把 HTTP 成功等同于业务成功。

#### 数据库

- 默认只读；写入必须获得授权，并先备份、校验环境和精确目标。
- 禁止操作生产数据库；禁止未经授权的 `DROP`、`TRUNCATE` 和破坏性 `ALTER`。
- 测试数据必须可识别、可隔离、可清理；清理前再次确认精确范围。
- 验证约束、关系完整性、孤儿记录、软删除、唯一键、并发和重复执行。
- 结构变更使用 `Expand → Migrate → Contract`：先兼容扩展，再回填和双读/双写验证，最后在独立发布中收紧合同。
- 同时验证全新安装和旧版本数据升级，不能只测空数据库。

### 3.17 真实业务流验证

以用户身份从入口完成完整流程，并重新查询结果。至少验证一次刷新或重新登录；涉及多角色时验证授权角色、下级角色和无权限角色。跨端任务应验证各端读取同一持久化结果。

### 3.18 失败修复循环

循环步骤固定为：收集证据 → 单一根因假设 → 最小修复 → 最窄重测 → 模块回归。禁止同时尝试多个无证据补丁。相同测试修复最多三轮；第三轮仍失败时停止，报告根因假设、已尝试内容、日志路径和所需决策。

### 3.19 代码审查

L2 以上由独立审查角色检查正确性、回归、权限、数据一致性、并发、错误处理、可维护性、测试真实性和越界修改。审查修复最多三轮；未解决的 HIGH/CRITICAL 问题阻止交付。

### 3.20 自动清理门禁

清理门禁只处理本任务创建且可明确识别的临时资源：临时文件、临时测试数据、进程、服务、端口占用和报告中的秘密。不得执行通用 `clean`、递归删除、清理用户文件或自动 stash。

清理报告记录：目标、所有者、创建时间、清理方式、结果和残留。任何无法证明归属的资源都不删除。

### 3.21 清理后的最终回归

清理完成后重新执行关键冒烟和持久化读取，防止测试依赖遗留进程、缓存或数据而产生假通过。

### 3.22 影响范围复查

比较最终 diff 与编码前影响清单。GitNexus 可用时运行 `detect-changes`；检查是否出现新调用链、共享合同或未计划文件。HIGH/CRITICAL 新影响必须先告警并重新评估风险与测试。

### 3.23 安全提交

提交前必须：

1. 复核 `git status --short`，区分用户变更和本任务变更。
2. 运行相关测试和清理后的最终回归。
3. 运行影响检查和 `git diff --check`。
4. 确认无秘密、构建产物、完整数据或越界文件。
5. 仅在明确授权后精准暂存本任务文件并提交。

未经授权不得创建/切换分支、提交、push、合并主分支、创建 PR 或部署。

### 3.24 最终报告

最终报告必须包括：

- 结果和业务影响；
- 风险等级与实际影响范围；
- 修改文件；
- 验收标准完成情况；
- 测试、浏览器、API、数据库和集成验证结果；
- Feature flag 和回滚方式；
- 清理结果；
- 未解决风险、占位符和后续动作；
- Git 状态，以及是否分支、提交、push、PR、部署。

不能将“命令启动”“HTTP 200”或“构建成功”单独当作业务验收通过。

## 4. 防止长时间静默和无限循环

- 持续工作期间不超过 60 秒无状态更新。
- 长任务使用不超过 60 秒的短轮询，报告当前阶段而非重复日志。
- 同一失败命令最多执行三次；第三次后停止并更换有证据的策略或报告阻塞。
- 同一测试修复最多三轮；同一审查修复最多三轮。
- 禁止无界重试、递归修复或“直到成功”为止的循环。
- 大日志、截图、trace 和机器可读结果保存到 `reports/ai/`；对话只给摘要和证据路径。
- 新用户指令到达时重新判断是否替换当前任务，避免继续执行过期工作。

## 5. 日常最小使用方法

1. 复制[任务模板](task-template.md)填写任务。
2. 完成需求表、Given/When/Then、影响清单和风险等级。
3. L2 以上输出角色所有权表与测试矩阵。
4. 运行基线，写失败测试，再做最小实现。
5. 按范围运行专项门禁、真实业务流和独立审查。
6. 清理本任务临时资源后完成最终回归与影响复查。
7. 未获授权只提交报告，不执行 Git 或外部发布动作。

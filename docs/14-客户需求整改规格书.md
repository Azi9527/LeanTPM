## 2. 整改目标

在 LeanTPM V1.0 既有设备基础、点检、维保、OEE、可视化和 Android 作业能力上，完成客户需求差距整改，使系统达到以下目标：

1. 形成独立的故障报修与维修工单闭环，并与设备状态、点检异常、维保异常联动。
2. Android 点检照片具备设备、任务、服务端时间和定位水印，原始证据可审计。
3. 点检项目、方案和设备适用关系支持 Excel 批量导入并返回逐行校验结果。
4. 点检结果支持日期区间、组织、班组、人员、设备和状态组合查询，并按数据权限导出。
5. 建立任务到期提醒、临时任务强提醒、逾期逐级升级、已读确认和发送审计。
6. 固化车间主任、班组长、操作工岗位权限模板，并验证不同数据范围之间不能越权。
7. 用户支持 Excel 批量导入、组织/角色映射、重复策略和错误回执。
8. 完成本地部署优先的生产基线，同时保留云端部署能力。
9. Android 增加轻量看板、系统通知、弱网重试和版本升级基线。
10. 所有整改项具备自动化测试、真实 MySQL 验证、前端构建、Android 构建和验收证据。

## 3. 范围与边界

### 3.1 本次范围

- P0：独立故障维修、照片水印、点检批量导入、结果区间查询与导出、提醒升级、岗位权限模板、用户批量导入、部署基线。
- P1：Android 轻量看板、Android 系统通知与弱网可靠性、二维码/微信边界确认。
- P2：验收追踪、指标口径、目标机型兼容、性能与安全证据包。

### 3.2 明确不做

- 不开发 iOS APP。
- 不开发微信小程序。微信仅作为二维码公共信息页的可选浏览器入口；正式点检和保养作业使用 Android APP。
- 不在本轮接入 PLC、IoT 网关或第三方 ERP/MES 实时接口，仅保留扩展接口。
- 不用 Mock 服务替代正式后端能力。
- 不在未确认客户部署环境前写死域名、证书、短信或推送供应商。

## 4. 总体设计原则

### 4.1 数据与迁移

- 新增表和字段全部通过 `V17` 之后的 Flyway 增量迁移交付，不修改已经执行的 V1～V16。
- 所有业务表继续包含 `tenant_id`、审计字段、逻辑删除和必要的乐观锁字段。
- 任务、消息、维修工单和导入批次必须具备业务唯一键或幂等键。
- 历史结果保存任务生成时的设备、标准、方案版本和组织快照，不依赖当前主数据反查历史事实。

### 4.2 安全与权限

- Controller 使用功能权限校验，Service 再校验资源数据范围。
- 导出、附件查看、扫码、异常转维修和消息升级均不能通过替换资源 ID 越权。
- 照片定位属于敏感信息，只允许任务执行人和授权管理人员访问。
- Android 访问令牌、刷新令牌、离线草稿和待上传证据继续使用 Android Keystore 保护。

### 4.3 可用性

- 所有批量导入先校验后落库，错误精确到工作表、行号、字段和原因。
- 所有长耗时导出支持限流；数据量超过同步阈值时进入异步导出任务。
- Android 离线提交使用客户端请求 UUID，恢复网络后服务端幂等处理。
- 到期提醒和逾期升级可配置、可停用、可审计，任务关闭后停止发送。

## 5. 整改项详细规格

## 5.1 ADJ-01 独立故障与维修闭环

### 业务范围

状态链路：

`已报修 → 待受理 → 待派工 → 维修中 → 待验收 → 已关闭`

允许的例外状态：`已驳回`、`已取消`、`挂起`。非法状态跳转返回 `409`。

### 数据模型

计划新增：

- `equipment_fault_report`：报修单、设备、故障时间、现象、等级、来源、报修人、附件、当前状态。
- `equipment_repair_order`：维修工单、主维修人、协作人、开始/暂停/恢复/完成/验收时间、工时、停机时长、维修结论。
- `equipment_repair_collaborator`：协作维修人员。
- `equipment_repair_material`：备件、数量、单价、总价。
- `equipment_repair_event`：状态事件和操作审计。
- `equipment_fault_attachment`：报修、维修、验收附件关系。
- 点检异常和维保异常增加可选 `repair_order_id` 关联。

### 后端接口

- `GET/POST /api/v1/faults/reports`
- `GET/PUT /api/v1/faults/reports/{id}`
- `POST /api/v1/faults/reports/{id}/accept`
- `POST /api/v1/faults/reports/{id}/reject`
- `POST /api/v1/faults/reports/{id}/repair-order`
- `GET/POST /api/v1/faults/repairs`
- `PUT /api/v1/faults/repairs/{id}/assignment`
- `POST /api/v1/faults/repairs/{id}/start|pause|resume|complete|acceptance`
- `PUT/DELETE /api/v1/faults/repairs/{id}/materials/{materialId}`
- `GET /api/v1/faults/statistics`
- `POST /api/v1/inspection/abnormalities/{id}/repair-order`
- `POST /api/v1/maintenance/abnormalities/{id}/repair-order`

### 前端与 Android

- Web：故障报修、维修工单、我的维修、故障统计。
- Android：扫码设备后可报修；维修人员可执行本人维修工单、拍照、填写措施和材料。
- 设备进入维修时联动为 `REPAIR`；验收关闭后按工单配置恢复 `IDLE`、`RUNNING`、`STOPPED` 或 `OFFLINE`。

### 权限点

- `fault:report:view/create/update/cancel`
- `fault:repair:view/create/assign/execute/accept/cancel`
- `fault:material:manage`
- `fault:statistics:view`

### 验收条件

1. 扫码报修后仅生成一张报修单。
2. 点检异常可一键转维修工单，重复点击不产生重复工单。
3. 工单状态机拒绝非法跳转。
4. 暂停时间不计入有效维修工时。
5. 停机时长、材料费用、故障类型可统计并下钻。
6. 非数据范围用户不能查看或操作工单。

## 5.2 ADJ-02 照片时间与定位水印

### Android 采集

- 使用原生定位能力采集经纬度、定位精度、地址文本、定位时间和提供方。
- 使用服务端时间与设备时间计算偏差；偏差超过系统阈值时显示告警并记录。
- 相机返回后生成水印预览，内容至少包括：设备名称/编码、任务编号、拍摄时间、经纬度或地址、执行人。
- 用户拒绝定位时按项目规则处理：允许说明后提交或禁止提交。
- 定位和相机权限均使用运行时授权，并提供用途说明。

### 服务端证据

- 扩展附件证据元数据：`captured_time`、`server_received_time`、`latitude`、`longitude`、`accuracy_meters`、`address_text`、`device_time_offset_seconds`、`original_sha256`、`watermarked_sha256`。
- 服务端验证任务、设备、用户和附件归属，不接受客户端直接指定其他任务的附件。
- 保留原图和水印图；下载权限遵循任务数据范围。
- 水印图应由服务端或可信原生流程生成，不能仅依赖前端 Canvas 展示。

### 安全调整

- Web 仍保持 `geolocation=()`；仅在 Android 原生插件中开放定位。
- 地理位置不写入日志明文，不提供公开二维码页面访问。
- 配置证据保留周期和清理策略。

### 验收条件

1. 水印可见且内容与任务一致。
2. 服务端能核对原图与水印图 SHA-256。
3. 无定位、低精度、时间偏差场景按配置执行。
4. 断网拍照恢复上传后时间和定位元数据不丢失。
5. 越权用户不能下载证据。

## 5.3 ADJ-03 点检项目与方案批量导入

### 模板

一个 Excel 文件包含：

- `点检项目`：项目编码、名称、分类、部位、内容、方法、工具、标准、结果类型、上下限、单位、必填、必拍、异常等级、安全说明。
- `点检方案`：方案编码、名称、周期、间隔、时间、默认执行人、班组、复核、有效期。
- `方案项目`：方案编码、项目编码、顺序和覆盖规则。
- `适用设备`：方案编码、设备编码或分类编码。

### 导入规则

- 支持仅校验和确认导入两阶段。
- 同一租户项目/方案编码唯一。
- 已发布方案不原地覆盖，只能产生新草稿版本。
- 设备、分类、用户、班组必须存在且在当前数据范围内。
- 一行错误不影响其他行校验；确认导入时采用批次事务策略。
- 返回新增、更新、跳过、失败数量及逐行错误。

### 接口与页面

- `GET /api/v1/inspection/import-template`
- `POST /api/v1/inspection/import/validate`
- `POST /api/v1/inspection/import/commit`
- `GET /api/v1/inspection/imports/{batchId}`
- 点检项目/方案页提供模板下载、上传、校验预览、确认和错误回执。

### 验收条件

1. 1000 个项目、200 个方案和 5000 条关系可在限制时间内导入。
2. 错误精确到工作表、行、列和原因。
3. 重复提交同一导入批次不产生重复数据。
4. 已发布方案历史不被修改。
5. 导入遵循当前用户数据范围。

## 5.4 ADJ-04 点检结果区间查询与导出

### 查询条件

- 时间口径：计划日期、执行时间、提交时间、完成时间。
- 起止日期/时间。
- 组织、班组、执行人、设备、方案、任务状态、是否异常、异常等级。
- `mineOnly` 与角色数据范围继续生效。

### 导出内容

- `任务汇总`：任务、设备、组织、班组、人员、状态、计划/截止/完成、完成率、异常数。
- `逐项结果`：项目、部位、标准、结果、单位、异常、执行人和执行时间。
- `异常记录`：异常状态、责任人、期限、措施、验证。
- `附件索引`：附件名称、类型、任务/结果/异常关系、上传时间；不直接将图片嵌入工作簿。

### 接口

- 扩展 `GET /api/v1/inspection/tasks` 查询参数。
- `GET /api/v1/inspection/results/export`。
- 数据量超过系统参数阈值时返回导出任务编号，并从附件中心下载结果。

### 验收条件

1. 查询与导出使用相同过滤条件和数据范围。
2. 员工、班组长、车间主任导出行数符合权限预期。
3. 日期边界、跨月、空结果和 10 万明细场景正确。
4. Excel 不出现公式注入风险。

## 5.5 ADJ-05 提醒与逾期升级引擎

### 数据模型

- `notification_rule`：业务类型、提前量、重复间隔、升级级别、渠道、启停。
- `notification_message`：接收人、标题、内容、业务资源、严重度、已读/确认状态。
- `notification_delivery`：渠道、发送时间、结果、失败原因、重试次数。
- `notification_escalation`：任务、当前级别、下次升级时间、最后通知时间。

### 规则

- 计划任务：到期前 N 分钟/小时提醒执行人。
- 临时任务：创建后立即产生高优先级消息并要求确认。
- 逾期任务：先通知本人，再按组织负责人/班组负责人逐级升级。
- 任务完成、取消或作废后停止后续提醒。
- 同一任务、接收人、规则、时间窗口内只能产生一条消息。

### 渠道

- 第一阶段必须实现系统消息和 Android 本地/系统通知。
- 短信、企业微信、邮件作为可插拔渠道，未配置时不得影响业务事务。

### 接口与页面

- `GET/POST/PUT /api/v1/notifications/rules`
- `GET /api/v1/notifications/messages`
- `POST /api/v1/notifications/messages/{id}/read|acknowledge`
- `GET /api/v1/notifications/deliveries`
- Web：提醒规则、消息中心、发送记录。
- Android：消息角标、锁屏通知、已读/确认、业务跳转。

### 验收条件

1. 到期前提醒、临时强提醒、逾期一级和二级升级均可自动触发。
2. 重复调度不产生重复消息。
3. 关闭任务后不再发送。
4. 无上级时记录明确原因，不静默丢失。
5. 通知失败可重试且不回滚业务任务。

## 5.6 ADJ-06 岗位角色与数据范围模板

### 角色模板

| 角色 | 默认数据范围 | 主要能力 |
|---|---|---|
| 系统管理员 | 全部数据 | 系统、主数据和全部业务管理 |
| 车间主任 | 所属组织及下级 | 车间设备、计划、任务、结果、异常、故障和看板 |
| 班组长 | 所属班组或自定义组织 | 班组派工、结果、逾期、异常和看板 |
| 操作工 | 本人数据 | 本人设备、点检、保养、维修和消息 |

兼容现有“计划员”，迁移时不删除已有角色；客户启用模板后可停用不需要的角色。

### 验收条件

1. 四类账号自动化验证列表、详情、导出、附件和写操作权限。
2. 修改 URL 资源 ID 不能越权。
3. 多角色按并集计算，任一全部数据角色正确覆盖。
4. 角色调整后新请求立即按新范围执行。

## 5.7 ADJ-07 用户批量导入

### 模板字段

账号、姓名、工号、手机号、邮箱、组织编码、角色编码列表、是否允许移动端、初始密码、处理策略。

### 规则

- 账号不可变且租户内唯一。
- 组织和角色使用编码匹配，禁止使用数据库 ID。
- 支持“仅新增”和“新增并更新”两种策略。
- 初始密码至少 6 位；首次登录必须修改。
- 模板不回显现有密码，不允许导出密码哈希。
- 错误行不落库，成功行记录导入批次和操作者。

### 接口

- `GET /api/v1/system/users/import-template`
- `POST /api/v1/system/users/import/validate`
- `POST /api/v1/system/users/import/commit`
- `GET /api/v1/system/users/imports/{batchId}`

### 验收条件

1. 1000 用户内导入完成并返回统计。
2. 重复账号、无效组织、无效角色和弱密码均准确报错。
3. 重复提交不创建重复用户。
4. 导入用户首次登录必须改密。

## 5.8 ADJ-08 部署方式与运维基线

### 默认建议

客户试点优先采用内网本地部署：

- Nginx/HTTPS 反向代理。
- Spring Boot 双实例或可滚动单实例。
- MySQL 8 独立实例。
- Redis 7 持久化实例。
- 附件目录独立磁盘并每日备份。
- Android 配置正式 HTTPS 服务地址。

### 必交付文档

- 部署调查表和网络拓扑。
- Secret、证书、域名、端口和防火墙清单。
- 数据库、Redis、附件备份恢复手册。
- 日志、监控、告警和容量基线。
- 升级、回滚、数据迁移和 APK 分发流程。

### 验收条件

1. 备份恢复演练通过。
2. 正式 HTTPS 证书链、HSTS、CORS 和代理头验证通过。
3. Android 在客户网络下可登录、扫码、上传和恢复断网草稿。
4. 密钥和密码不写入 Git 或安装包。

## 5.9 ADJ-09 Android 轻量管理看板

### 指标

- 今日应检、完成、待办、逾期、异常、完成率和按时率。
- 按车间/班组的完成率、逾期数和异常数。
- 逾期清单按逾期时长排序并可下钻任务。
- 指标严格遵循当前用户数据范围。

### 验收条件

1. Android 与 Web 同一时间范围、同一权限下指标一致。
2. 常用手机宽度无横向滚动。
3. 指标可下钻到本人、班组或车间清单。

## 5.10 ADJ-10 二维码与微信边界

- Android APP 扫码：登录后进入设备现场页并显示本人任务。
- 微信/浏览器扫码：仅进入免登录公共设备信息页，不允许执行点检、查看负责人、附件或敏感参数。
- 所有正式二维码使用 HTTPS 可达地址和随机不可推断令牌。
- 客户如后续要求微信内执行点检，作为独立变更评估，不在本轮范围。

## 5.11 ADJ-11 Android 通知与弱网可靠性

- 系统通知点击后进入对应任务/异常/维修工单。
- 待上传请求写入加密队列，使用请求 UUID 幂等重试。
- 附件支持压缩、超时、失败重试和网络类型提示。
- APP 展示版本并支持后台配置最低支持版本、下载地址和升级说明。
- 正式包使用企业 keystore；Debug 包不得用于生产。

## 5.12 ADJ-12 验收口径与证据包

- 每个整改项维护需求编号、设计、代码提交、测试、验收证据和状态。
- 自动化测试报告、数据库迁移报告、前端构建、APK 信息和 SHA-256 纳入交付记录。
- 真机、性能、安全和部署环境无法在开发机完成的项目必须明确标记“环境待验”，不能伪造通过结论。

## 6. 数据库迁移规划

| 迁移 | 主题 | 主要内容 |
|---|---|---|
| V17 | 整改基础与导入批次 | 通用导入批次/错误、客户岗位模板、系统参数和权限点 |

## 7. 接口通用约束

- 响应继续使用 `code/message/data/timestamp`。
- 所有写接口使用 `Idempotency-Key` 或业务唯一键防重复。
- 分页接口限制 `pageSize`，导出接口限制最大数据量。
- 上传文件检查扩展名、MIME、文件头、大小和病毒扫描扩展点。
- Excel 文本以 `= + - @` 开头时按文本安全导出，防止公式注入。
- 位置、附件和导出接口必须执行服务端数据范围校验。

## 8. 前端与 Android 交互规范

- 页面统一提供加载、空数据、失败重试、无权限、重复提交保护。
- 批量导入必须先显示校验摘要，用户确认后才落库。
- 状态、优先级和异常等级同时使用文字与颜色，不只依赖颜色。
- Android 必须适配安全区域、系统字体放大和 360px 以上常用宽度。
- 定位、相机、通知权限被拒绝时提供明确原因与设置入口。
- 离线状态和待同步数量在工作台持续可见。

## 9. 测试规格

### 9.1 后端单元测试

- 状态机、导入校验、提醒幂等、升级路径、密码策略、数据范围和照片元数据校验。
- 边界值：空值、最大长度、跨日期、时区、零/负数、重复请求和乐观锁冲突。

### 9.2 真实 MySQL 集成测试

- 空库完整执行 V1～最新迁移。
- 导入校验/提交/重复提交/错误回执。
- 四类角色列表、详情、导出和写操作权限。
- 到期、临时、逾期一级/二级升级和任务关闭停止提醒。
- 报修、维修、暂停、材料、验收和异常转单。
- 照片证据元数据、附件权限和哈希一致性。
- 临时测试库必须在成功或失败后自动删除。

### 9.3 前端测试

- `npm run typecheck`
- `npm run build`
- 关键页面组件和 API 参数测试。
- Playwright：导入预览、结果筛选导出、提醒规则、故障工单、权限不可见/不可操作。

### 9.4 Android 测试

- Web 资源构建与 Capacitor 同步。
- Android 单元测试和 Debug 构建。
- APK 签名、清单、minSdk/targetSdk、明文网络策略检查。
- 真机：登录、扫码、定位、拍照水印、断网草稿、恢复上传、系统通知和升级提示。

### 9.5 发布门禁

必须同时满足：

1. Git 空白检查通过。
2. 后端单元测试 0 失败、0 错误。
3. 真实 MySQL 集成测试 0 失败、0 错误、0 跳过。
4. 前端类型检查和生产构建通过。
5. npm 高危漏洞为 0。
6. Android 单元测试和 Debug 构建通过。
7. 数据库备份恢复和迁移重放通过。
8. 无法在当前环境执行的真机/生产域名项目明确列入环境待验清单。

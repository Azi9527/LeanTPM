# 用户导入统一组织负责人修复

## 需求

- 用户导入只保留一个“负责组织编码”字段。
- 车间、产线/工段、班组以及其他现有组织节点均复用 `organization.manager_user_id`，不新增负责人字段。
- 客户现有模板的“负责组织编码列表”继续可导入，但同一用户只能填写一个负责组织。
- 导入成功后，组织负责人关系为单人关系；不再累加多名负责人。
- “人员与组织关系”页面的负责人选择统一为单选；车间、产线/工段和班组共用同一负责人合同。
- 负责人仅要求是启用账号，不再与“车间主任/班组长”等权限角色强耦合；角色继续独立表达权限。
- 本任务仅修改源码和测试，不部署、不修改云端数据库或服务。

## Given / When / Then

1. Given 启用的 `LINE-FX` 或 `LINE-QM` 组织，When 用户导入填写该组织为负责组织，Then 校验通过并将导入用户写入该组织现有 `manager_user_id`。
2. Given 新版模板，When 下载模板，Then 表头和说明使用单数“负责组织编码”。
3. Given 客户现有旧模板，When 表头仍为“负责组织编码列表”且仅填一个编码，Then 继续兼容。
4. Given 一个单元格填写多个负责组织，When 校验，Then 返回明确错误且不进入提交数据。
5. Given 同一文件两行声明负责同一组织，When 校验，Then 两行不能以最后写入覆盖前一行，冲突行返回明确错误。
6. Given 组织已有历史负责人关系，When 导入新负责人，Then `manager_user_id` 与兼容关系表都只保留本次导入的一个负责人。
7. Given 车间下存在产线/工段或直接存在班组，When 管理员维护负责人，Then 两种层级都可设置一个负责人且不要求新增字段。
8. Given 任意负责人接口提交两名用户，When 后端处理，Then 以 `ORGANIZATION_MANAGER_MULTIPLE_NOT_ALLOWED` 拒绝，不能只保存第一名。

## 影响分析与风险

- GitNexus 对 `UserImportService` 类的精确影响为 LOW：3 个直接依赖（系统控制器、导入集成测试）。
- 负责人 PUT 路由的 GitNexus API 影响为 LOW（未识别到其他前端消费者）；Java 重名方法的索引解析仍异常扩散，因此公共请求结构保持兼容，仅把列表约束为最多一个用户。
- 涉及 Excel 合同、事务内组织负责人持久化和数据权限，按 L2 执行。
- 不新增数据库迁移；复用现有 `organization.manager_user_id` 和现有兼容关系表。

## 多角色治理与所有权

- 实现角色：修改用户导入服务、人员组织关系服务/Mapper、关系页面及模板文案；不改数据库结构。
- 测试角色（只读复核阶段）：新增/调整用户导入和单负责人服务测试及 MySQL 集成测试，不修改生产逻辑。
- 审查角色（只读复核阶段）：检查旧模板兼容、单负责人不变量、数据权限、乐观锁和用户既有改动保护。

- 失败测试先行：旧实现因缺少启用用户通用校验方法而编译失败，证明新合同尚未实现。
- 后端窄测：9/9 通过（统一负责人导入 4 项、人员组织关系 5 项）。
- 后端全量测试：159 项，失败 0、错误 0；其中 60 项需要隔离 MySQL 环境变量而跳过。
- 前端 `vue-tsc` 类型检查通过，生产构建通过。
- GitNexus 最终精确复核：`UserImportService` 为 LOW（3 个直接依赖），`SystemService` 为 MEDIUM（9 个直接依赖）；全量测试已覆盖该共享服务。全工作树因用户既有 89 个变更文件被汇总为 CRITICAL，不能归因于本任务。
- `git diff --check` 通过；本任务没有创建进程、服务、端口、数据库或外部资源，无需清理。Maven `target` 与前端 `dist` 均为既有忽略构建目录，未删除。

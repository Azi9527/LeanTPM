# 设备名称与编号展示完整性优化

## 需求

1. Web 与 APP 的客户可见界面中，凡展示具体设备名称且当前接口已经提供设备编号时，必须在同一信息块内同时展示设备编号，避免同名设备无法区分。
2. Web 点检方案版本详情的“指定设备”必须显示“设备编号 · 设备名称”。
3. APP“设备现场信息”的“管理信息”首次进入默认展开，同时保留手动收起/展开能力。
4. 不改生产环境、不改数据库、不提交、不推送、不部署；保护工作区既有变更。

## 验收条件（Given / When / Then）

- Given 两台设备名称相同、编号不同，When 用户查看方案版本详情、任务卡片、异常、维修、设备状态履历或可视化风险列表，Then 每个设备信息块均能看到对应编号和名称。
- Given 用户打开 APP 设备现场信息，When 页面首次渲染成功，Then “管理信息”内容可见，按钮显示“收起”；When 用户点击按钮，Then 仍可切换为折叠。
- Given APP 扫描到与任务不匹配的设备，When 显示不匹配提示，Then 目标设备与当前设备均优先显示“编号 · 名称”。
- Given 页面原本已在同一表格行、卡片或标题邻近位置展示编号，When 本轮审计，Then 不重复添加第二份编号。

## 审计边界

- 包含：`frontend/src/views` 与 `LeanTPM-APP/pages` 的客户可见设备实体展示，以及包含设备名称的确认/错误提示。
- 排除：表单字段名、搜索占位、API 类型定义、照片水印模板变量、仅用于路由或缓存的内部字段。
- 已确认无需改后端合同：本轮命中的任务、异常、维修、状态、可视化和设备台账对象均已返回 `equipmentCode`；方案详情可由已加载的设备台账按 `equipmentId` 映射编号。

## 影响分析与风险

- GitNexus 查询已定位方案详情、APP 设备现场信息和设备身份展示链路。
- 修改前对相关 Vue 状态/方法执行 upstream impact：16 个目标均为 LOW；APP `scan` 有 1 个直接页面入口，其余目标无上游调用或执行流扩散。
- 风险等级：L2。原因是跨 Web/APP 多个展示面的一致性调整；不涉及 API、持久化、权限规则或部署。

## 多角色治理（单代理分阶段）

- 需求/架构角色：只定义显示规则和审计边界，不写业务实现。
- 实现角色：仅拥有本报告列出的 Web/APP 页面和新增合同测试，不修改 Backend、部署或运行时目录。
- 测试角色：以失败优先的静态 UI 合同测试、现有 APP/Web 测试和构建结果作为证据。
- 审查角色：只读复核 diff、GitNexus detect-changes、影响复查与 `git diff --check`。

## 测试优先计划

1. 先新增 Web/APP 设备身份展示合同测试，并确认在当前实现上失败。
2. 最小修改命中页面，不引入设备身份新数据源。
3. 运行 APP verify、Web test/typecheck/build；因无 Backend 合同变更，本轮不新增 Backend 测试，但最终仍结合上一轮完整 Backend 结果说明发布边界。

## 实现结果

- Web 点检方案版本详情的指定设备统一为“设备编号 · 设备名称”。
- Web 补齐点检/保养移动任务、点检/保养异常、维修工单、点检派工、设备状态履历、计划/设备删除确认和可视化风险列表中的设备编号。
- APP 补齐工作台待办、点检详情、异常列表和扫码设备不匹配提示中的设备编号；待执行任务进入扫码页时同步携带设备编号。
- APP 设备现场信息的管理信息默认展开，用户仍可点击“收起/展开”。
- 二次审计确认：其余客户可见设备名称均已在同一卡片、同一表格行或标题紧邻位置显示编号；照片水印、路由缓存、表单字段与搜索占位不属于遗漏。

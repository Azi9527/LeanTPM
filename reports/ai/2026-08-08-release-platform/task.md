## 3. 真实问题与明确需求

### 3.1 真实问题

当前系统无法用机器可验证和可重放的证据回答：

1. 哪个可信提交、产品版本、配置引用、数据库 schema、Web 与 APP 制品组成一次发布；
2. 目标 Windows Server 是否满足升级前提，谁批准并执行了每一步；
3. 发布包是否完整、未被篡改、来自可重复构建且没有夹带秘密或客户资料；
4. 迁移、备份、切换或健康验证失败后能否安全停止、前滚或恢复；
5. 运维控制面失陷时，能否被限制在受审计的命令白名单，而不是获得业务 Secret、数据库管理员或任意 shell 权限。

### 3.2 已核实现状

- 后端 Maven `1.0.0`；Web package/lock `1.0.1`；旧 Capacitor Android `1.0.1/code 2`；新 uni-app `1.0.0/code 100`；数据库 Flyway `V48`。
- 无单一版本源、正式发布 tag、根变更日志、release-manifest、schema、校验器或可验证发布包。
- `V1` 到 `V48` 迁移连续存在，但 `MySqlMigrationIntegrationTest` 仍断言 34 条成功迁移，发布脚本/旧手册仍写 V1-V32。
- 现有验证没有生成生产级机器可读结论；跳过 MySQL 时没有明确标成 `NOT_RELEASEABLE`。
- MySQL 测试脚本存在开发默认凭据和命令行传密风险；报告不得记录其值。
- 备份/恢复只覆盖 MySQL，不覆盖附件、配置、Secret 引用、备份集清单和恢复后验收。
- 部署资产为 Linux systemd/Nginx 示例；没有 Windows Service、一键发布/回滚或 Windows 最小权限方案。
- 只有聚合 `/actuator/health`；没有独立 startup/readiness/liveness 语义和构建版本信息。
- Web 有 package-lock v3；新 uni-app 依赖外部 HBuilderX，缺少仓库内工具链锁与正式构建可重复性证据。
- 现有 APP 发布管理位于业务后端，只管理当前 APK，不是主机发布平台或独立运维控制面。
- 旧交付报告仅作背景，不作为本任务当前通过证据。

## 4. 决策、假设与待环境确认

### 4.1 可逆开发假设

- 首个统一候选产品版本暂用 `1.0.1`，因为 Web 与旧 Android 已使用该 versionName；这只是仓库候选，不是正式 tag、生产版本或发布批准。
- 新 uni-app versionCode 候选为 `101`，高于仓库已知的 `100` 与旧 Android `2`；进入正式签名/覆盖升级前必须核对客户实际已发布最高值。
- 产品版本采用 SemVer；数据库 schema 保持 Flyway 整数版本并由 manifest 映射，不伪装成 SemVer。
- 第一阶段服务包装器按“外部受信任 WinSW 制品 + 固定版本/哈希 + 仓库内配置与验证脚本”设计，不把未授权第三方二进制加入仓库。
- Windows 路径、端口、域名、证书、服务账号、Secret provider 和备份介质全部参数化，不硬编码客户值。
- 默认 RPO/RTO 设计目标沿用现有文档的 `RPO <= 15 分钟`、`RTO <= 4 小时`，最终值须环境评审批准。

### 4.2 进入环境集成前必须确认

- Windows Server 版本、单机/双机、反向代理产品与网络拓扑；
- 正式 APP 已发布最高 versionCode、已部署产品/schema 版本与支持的最旧升级版本；
- WinSW 或等效包装器来源、允许版本与供应链验证方式；
- 服务账号、目录、端口、证书来源、Secret 管理产品与轮换责任；
- 离线拷贝、共享目录、制品库或 CI 的发布包传递方式；
- manifest 签名信任根、证书轮换和双人审批策略；
- 运维控制面同机还是独立主机、身份源、告警渠道与审计保留期；
- 备份介质、加密/KMS、异地复制与正式 RPO/RTO；
- APP 是否只交付 Android，或还要求 H5/微信生产制品。

## 7. L4 风险、威胁与最小边界

### 7.1 风险分级

- 最高等级：L4 / CRITICAL 治理级别。
- 原因：发布主链、数据库升级、权限/Secret、Windows Service、共享版本合同、回滚与恢复跨模块联动。
- 缩小边界：第一阶段只实现离线、参数化、默认人工确认、可 WhatIf、命令白名单和 fail-closed 资产；不扩权现有业务后端，不写生产，不实现任意 shell；控制面另进程、另账户、另端口、另数据存储。

### 7.2 主要威胁

| 威胁 | 典型风险 | 控制 |
|---|---|---|
| Spoofing | 伪造发布人、包或目标环境 | 独立认证、签名信任根、目标环境标记、审批身份 |
| Tampering | 替换 JAR/Web/APK/迁移/manifest | 逐文件 SHA-256、detached signature、额外文件拒绝、不可覆盖 release ID |
| Repudiation | 发布/回滚无责任链 | 追加式审计、批准人与执行人、状态机和每步结果 |
| Information disclosure | Secret 出现在参数、日志、包、报告 | Secret 引用、环境/凭据提供器、日志脱敏、包清单拒绝 |
| Denial of service | 并发发布、服务停止超时、依赖故障 | 全局锁、超时、磁盘预检、readiness、失败停止与旧版本保留 |
| Elevation of privilege | 控制面执行任意命令或持有 DB 管理员 | 版本化命令白名单、强类型参数、最小服务账户、业务/运维 Secret 分离 |
| Path traversal | 包路径或备份路径越界 | 绝对路径解析、根目录约束、拒绝 `..`/链接/大小写碰撞 |
| Supply chain | 包装器/HBuilder/依赖被替换 | 工具链锁、来源与哈希、npm ci、签名校验、无隐式下载 |

## 9. 第一阶段验收标准

### 9.1 固定可信发布基线

```text
Given clean detached 工作树且 HEAD 等于可信提交
When 运行基线预检
Then 生成 commit、工作树、工具版本、批准文件范围和 dirty=false 的机器记录
And 原工作区用户文件和状态不发生改变
```

- HEAD 不匹配、dirty、未知文件、浅克隆无法证明、GitNexus 异常均不可发布。
- 并发固定同一提交必须产生相同摘要且不得覆盖发布 ID。

### 9.2 统一系统版本

```text
Given 合法单一版本源、产品候选版本和单调 APP versionCode
When 执行同步与校验
Then 后端、Web、APP versionName 和发布包版本一致，DB schema 独立映射
And 漂移、非法 SemVer、缺文件、versionCode 非递增或最低版本越界均失败
```

- 不修改业务实体乐观锁 `version` 语义。
- 同一输入重复校验幂等；并发版本提升必须冲突或被锁阻止。

### 9.3 release-manifest 与发布包

```text
Given 批准的构建产物与签名身份引用
When 创建并验证发布包
Then 固定目录、manifest、逐文件 SHA-256、签名信息和兼容/回滚信息一致
And 篡改、遗漏、额外文件、未知 schema、路径穿越、链接或大小写碰撞 fail closed
```

- 私钥和真实配置不入包；只有验证公钥的一方不能签名。
- 相同输入和固定时间戳重复打包应得到相同内容哈希；已存在包不得静默覆盖。

### 9.4 发布验证

```text
Given 完整候选与所需依赖
When 运行聚合门禁
Then 后端、Web、APP、manifest、迁移、索引、安全和签名生成机器可读结论
And 任一步失败立即停止；跳过数据库或 Release APP 时只能是 NOT_RELEASEABLE
```

- 工具缺失、依赖失败或 Secret provider 不可用均不得静默跳过。
- 迁移数量从实际文件/schema 合同推导，不再硬编码旧数字。

### 9.5 Windows Service

```text
Given 已验证包、受信任包装器、低权限账户、受控目录和空闲端口
When 安装、升级、启停或卸载隔离命名服务
Then 操作幂等、超时受控、readiness 正确、重启后恢复且旧版本可回切
And 卸载只移除该服务注册，不删除数据、附件、日志、备份或其他服务
```

- 路径含空格/非 ASCII、端口占用、磁盘不足、停止超时与并发升级均安全失败。
- 管理员安装权限与运行账户分离；服务包装不改变业务 JAR 合同。

### 9.6 完整备份与恢复

```text
Given 明确一致性窗口、精确源与唯一空目标
When 创建或恢复备份集
Then DB、附件、非敏感配置、Secret 引用、release manifest、哈希和加密元数据构成原子集合
And 任一子项失败使整套备份无效；非隔离或非空恢复目标默认拒绝
```

- 空附件、大文件、长路径、并发写入、空间不足和重复备份均有明确行为。
- `AllowNonEmpty` 不能成为生产默认路径；恢复后校验 Flyway、核心表、附件和登录/核心读取。

### 9.7 HTTPS、Secret 与健康

```text
Given 可信证书、受控 Secret、可写数据目录和健康依赖
When 启动并访问 HTTPS、startup、readiness、liveness
Then TLS/安全头正确，liveness 不因外部依赖失败而误杀，readiness 准确阻断流量
And 匿名健康响应只暴露最小状态，不泄露 Secret 或详细配置
```

- 证书过期/链不全、JWT Secret 缺失、目录不可写应启动失败或 readiness 失败。
- 旧 `/actuator/health` 保持受控兼容；业务认证、CORS、APP HTTPS 不回归。

### 9.8 一键发布/回滚

```text
Given 已批准且验签通过的候选和健康旧版本
When 操作者明确确认发布
Then 按锁→预检→验签→备份→暂存→迁移→切换→健康/冒烟→审计执行
And 任一步失败立即停止，只做预定义补偿并保留旧版本、备份和失败证据
```

- 默认人工确认；无批准、命令不在白名单、备份/验签/健康不可用时拒绝。
- 同 release ID 重复执行返回已有结果；不同 release ID 并发被锁拒绝。
- Expand/Migrate 阶段允许应用回切；Contract 必须独立发布。

### 9.9 隔离升级、回滚和恢复演练

```text
Given 明确 NON_PRODUCTION 标记、受支持旧备份和隔离 Windows/MySQL 目标
When 恢复、升级、故障注入、回滚/前滚并重新读取
Then schema、数据、附件、登录和核心业务结果一致，RPO/RTO 有计时证据
And 生产端点、原工作区和非本轮资源均未触及
```

- 空库、受支持最旧 schema 和脱敏近容量数据均需覆盖。
- 无隔离标记、host/库名/路径不匹配、磁盘满、依赖中断或服务超时均 fail closed。
- 清理只处理本轮唯一 ID 创建且可证明归属的资源。

## 10. 第二阶段验收边界

```text
Given 第一阶段已由当前证据完整验收
When 启动独立运维控制面
Then 它使用独立进程、端口、服务账户、认证、数据存储和版本化命令白名单
And 控制面不可用不影响业务服务，控制面失陷不直接获得业务 Secret、DB 管理员或任意 shell
```

- API/UI 覆盖发布记录、审批、服务启停、日志、健康、备份恢复、告警和审计。
- 不接受任意命令、SQL、URL 或路径；参数必须强类型并限制在批准根目录。
- 测试环境自动部署与生产审批式部署必须通过越权、并发、故障、幂等和审计验证。
